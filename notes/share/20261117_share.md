# 他のプロジェクトへ渡すもの（2026-11-17 時点）

南関競馬の予想プロジェクトで積み上げたもののうち、**他のプロジェクトでもそのまま使える部分**を
1枚にまとめたもの。競馬を知らなくても読めるように書いてある。

---

## A. 仕事の進め方（これがいちばん移植できる）

### A-1. ユーザーが確認した形を、こちらの判断で作り替えない

> 「なんでカエルの？！」「勝手なことするな」「10R最初と違うよ！」

この3つはどれも、**こちらが「良くなるはず」と思って形を変えたとき**に出た言葉。
自分が見つけた理由は、**形を変える理由にはならない**。

- 気づいたことは**言葉で報告する**。変えるかどうかはユーザーが決める
- 挙動を変えるときは**必ず戻す口（フラグ）を残す**
- 変えたあとは「**付けなければ前と完全に同じ**」をバイト比較で確かめて、そう報告する

実際の形 ── 新しい既定にしたものには全部、旧に戻す口が付いている
（`--pos-median` / `--swapdu` / `--no-futatsu` / `--sagaru` / `--dan-nama` / `--no-suitei` …）。

### A-2. 数字は引用する前に取り直す。覚えている数字を書かない

記憶から書いた数字が2回続けて違っていたことがある。
**集計結果を持つ json は黙って古くなる**ので、元データを足したら作り直す口を必ず回す。

★ さらに踏み込んだ失敗 ── **「同じ名前の違う数字」が2か所にあった。**
　表（`hyo.txt`）の「4角」と、図が馬を置いている横位置が別の計算だった。
　表の数字で集計して「前が58.3%／中が44.4%」と報告したが、
　**図から数え直すと50.0%／53.8%で逆転**していた。
　→ **ユーザーが見ている画面の数字で数える。** 中間ファイルの同名カラムを信用しない。

### A-3. 検証の範囲はユーザーが決める

このプロジェクトの最優先ルールは「**過去の開催に遡って測りに行かない**」。
こちらから「母数を増やしましょう」「別期間で検証しましょう」と**持ちかけない**。
言われたときだけ測る。

理由は、勝手に広げた検証がそのまま方針変更の口実になってしまうから。
**測る／測らないの決定権をユーザーに残す**という設計。

### A-4. 外した日は、外した理由を同じ日のうちに書く

`notes/live/YYYYMMDD_場.md` に、その日の数字と**自分がどこで間違えたか**を書く。
翌日それを読んでから作業に入る。言い訳を書かない。数字と、ユーザーの言葉をそのまま残す。

### A-5. 検証の軸を取り違えていないか疑う

「44鞍すべてが水準より遅い」という結果が出たことがある。
原因は**後半3Fを前半3Fの水準と比べていた**こと。構造的に必ずそうなる比べ方だった。
→ **全部が同じ向きに出たら、まず測り方を疑う。**

## B. 作ったもの（ツールの形）

全部 `scripts/ana/` にある Python。標準ライブラリ中心。

| 役割 | ファイル | 備考 |
|---|---|---|
| 当日のワンコマンド | `tojitsu.py` | 取得 → 図 → 画像 → 表 を1本で |
| 図の本体 | `tenkai_zu.py` | HTML/CSSを吐いて Chromium でPNG化 |
| 出馬表 | `syutuba.py` | スクレイプ。表記変更で壊れた履歴あり |
| 結果 | `kekka.py` / `capture.py` | 当日に取る（時間が経つとマスクされる） |
| 元データ蓄積 | `harvest.py` → `harvest/` | ここから各種 json を `--build` |
| 読み方の手順 | `nerai.py` | 図から買い／消しを機械的に出す |

### B-1. 図をHTML+CSSで作ってPNGにする

グラフライブラリを使わず、**位置を px で持つ `<div>` を並べたHTML**を書き、
ヘッドレス Chromium でスクリーンショットを撮っている。利点は

- CSSだけで見た目を変えられる（色・字・縁取り・帯）
- 要素の座標がHTMLに残るので、**あとから数えられる**（これが効いた）
- 画像の差分検査が楽（同じ入力なら完全一致するか確認できる）

```
chromium --headless --disable-gpu --no-sandbox --hide-scrollbars \
  --window-size=1100,1500 --force-device-scale-factor=2 \
  --screenshot=out.png "file://zu.html"
```

### B-2. 「後から足すスクリプト」は必ず本体に取り込む

帯や見出しの行を、最初はスクラッチパッドの使い捨てスクリプトでHTMLに注入していた。
**コンテナが作り直されると消える**ので、落ち着いた時点で本体のフラグにした。
→ 使い捨てで試す → 形が決まったら口にする、という順番は良い。**ただし必ず取り込む。**

### B-3. フラグの付け方

```
--obi      図を3等分して帯を敷く
--nige     見出しの下に1行
--age      見出しの下に2行
--anatag   条件に合う対象を目立つ札で強調
--plain    対外用。数値の札をまとめて落とす
--no-pct   説明文だけ差し替える（--plain とは別物）
```

**対外用（`--plain`）と内部用を別の口にしている**のが肝。
「お客さんに見せる版」と「自分が読む版」で出す情報が違うため。

## C. 読み方（この分野に依存するが、考え方は移植できる）

### C-1. 予測値は「順位」ではなく「帯」で使う

図が予想した位置は**平均0.235ずれる**（13個並ぶなかで±3個）。
だから「何番目か」は当てられない。**前／中／後ろの3つに割れば使える。**

→ **一般化** … 予測の誤差を測ってから、その誤差で潰れない粒度まで**わざと粗くする**。

### C-2. 単独の指標は効かない。2つ揃って効く

- 位置だけ … 前の帯50.0% / 中の帯53.8%（**差がない**）
- 終いだけ … 単独では基準と変わらない
- **位置 × 終い** … 52.2% 対 8.8%（基準22.9%）

→ **一般化** … 相関の弱い2軸を掛け合わせる。1軸で順位付けしない。

### C-3. 「拾う」より「消す」のほうが安定する

条件に合わないものを外す側（8.8%）のほうが、拾う側（52.2%）より安定していた。
→ **一般化** … 分類器を作るなら、まず**明確に落とせる群**を見つける。

### C-4. 誤差の大きい指標を、小さい指標で上書きしない

「押し上げ幅が大きい」で選んで外した。来たのは**上げ幅 +1〜+2 の馬**。
**+3以上 33.3% 対 +1〜+2 27.0%** で、差は6ポイントしかなかった。
→ **一般化** … 向きが出ている指標でも、**大小の順序まで信じない**。

## D. 数字を書くときの作法

- **いつの、どの母数か**を必ず添える（例「11/17 大井の11鞍140頭」）
- **分母と分子を両方書く**（「52.2%」ではなく「23頭中12頭＝52.2%」）
- **基準線を併記する**（「基準22.9%」）
- **1日分のものは「1日分」と書く**。他の日と並べない
- **結果を見てから区切りを決めた**ときは、そう書く

## E. 引き継ぐときの注意

1. **元データのディレクトリが空のまま `--build` 系を回すと、集計 json が壊れる**
   （590KBのファイルが2バイトになった）。回す前に中身を確かめる。
2. **cookie を持つ設定ファイルは絶対にコミットしない**（`.gitignore` 済み）。
3. **スクレイプ先の表記は黙って変わる。** 正規表現が空振りしても例外にならず、
   値が `null` のまま進む作りだと気づけない。**読めなかったら止まる**ようにする。
4. **使い捨てスクリプトはスクラッチパッドに置く。** リポジトリに混ぜない。
   ただし**形が決まったら本体に取り込む**（B-2）。
